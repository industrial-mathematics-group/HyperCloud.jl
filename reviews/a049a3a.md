### Findings

#### 1. 2-D BGK runs fail on the KernelAbstractions backend; the required `ka_cpu` suite fails at this commit — high — CONFIRMED
- **Where:** `test/sims_bgk.jl:66-82` (fails under `HYPERCLOUD_BACKEND=ka_cpu`); the kernel launch is HyperCloudCore 0.7.9 `foreach_particle` (`Backend.jl:119`, `KABackend` with a static work-group size of 256) for `_rhs_flux!` with `BGKEquation{2, 36}` and `MUSCL{2, 36}`.
- **What/scenario:** with 36 state components in 2-D the `_rhs_flux!` kernel's private memory limits PoCL to 231 work-items per group, but the backend always launches 256. `run_bgk_simulation` throws `ArgumentError: Work-group size (256, 1, 1) has more than 231 work-items, the maximum for this kernel` on the first step; the runner logs it and returns `nothing`. 1-D BGK with 48 equations still fits, so the limit depends on state size × dimension; 36 equations in 2-D already exceed it, so larger 2-D models (Chu pair, finer velocity grids) and 3-D models will too (not tested individually). The repo's own rules ask for the `ka_cpu` variant whenever kernels are touched, and "runs must work on the GPU path"; `test/gpu/runtests.jl` has no BGK case at all, so whether ROCm hits the same per-kernel limit (register pressure) is untested.
- **Evidence:** `ka_cpu_suite.log` (sims-bgk: 21 pass, 3 fail); `probe_ka_bgk.out` (2-D fails, 1-D 48 equations runs).
- **Fix:** in HyperCloudCore, launch with a work-group size that respects the kernel's limit (query the compiled kernel's maximum, or let KernelAbstractions pick it, `workgroupsize = nothing`/fallback on this error); in HyperCloud, add a small 2-D BGK case to `test/gpu/runtests.jl`. Until then, mark the 2-D BGK testset broken under `ka_cpu` or document the limitation.

#### 2. `burgers_kinetic` runs past the shock-formation time and compares against a wrong "exact" solution — medium — CONFIRMED
- **Where:** `src/Examples/burgers_kinetic.jl:18` (`:tmax => 2.0`, comment "Shorter tmax for Burgers before the shock gets too steep"); reference closure `src/PDEs/burgers.jl:41-78`; docs `docs/src/examples.md:45` say "up to `tmax = 1.0` … breaks at t* ≈ 1.17, so the run stays in the smooth regime".
- **What:** for `u0 = exp(-x²)` the breaking time is `1/max(-u0') = 1/sqrt(2/e) = 1.1658`. The example runs to 2.0 with 25 snapshots, so ~10 snapshots lie after the shock forms. The closure solves `u = u0(x - u t)` with Newton, which past breaking has three roots; it returns whichever branch Newton finds (or warns "did not converge" and returns the last iterate). This is not the entropy solution and does not conserve mass. `reference = "analytical_solution"` is used for the stats, so the reported errors of both methods are against a wrong reference.
- **Evidence:** `probe_analytic.out`: ∫u dx over the domain is 1.7724539 at t = 0 and t = 1.0, **1.3839 at t = 1.5 (−21.9 %)** and **1.2907 at t = 2.0 (−27.2 %)**; 1751 "Newton-Raphson did not converge" warnings while integrating at t = 1.5 and 2.0.
- **Fix:** set `:tmax => 1.0` as documented (or below 1.16), and make the Gauss closure detect `t ≥ t_b` (for the D-dimensional pulse `t_b = w e^{1/2} / (a √(2D))` along the diagonal (1.1658 for the example, 0.58/0.41 for the unit test's width 0.5 in 1-D/2-D); or simply check `dF/du ≤ 0` during Newton) and error or warn once instead of returning a wrong branch.

#### 3. `burgers_kinetic`'s kinetic method `ARS222MUSCL2` does not exist; half of the example never runs — medium — CONFIRMED

The doc (`docs/src/examples.md:49`) advertises `ARS222MUSCL2 (kinetic, IMEX)`.

#### 4. The `examples` test group cannot fail and, after the first run, does not even run the examples — medium — CONFIRMED

#### 5. Documented Euler representations `:primitive` / `:lagrangian` crash with `UndefVarError` — medium — CONFIRMED
- **Where:** `src/PDEs/_main.jl:22-35` construct `Primitive(...)`, `Lagrangian(...)`, `LinePath()`, `MappedPath()`, `NaiveAveragePath()`; none of these types is defined in HyperCloud or in HyperCloudCore 0.7.9 (grep finds no definition). Advertised in `docs/src/configuration.md:40-42` and `docs/src/PDEs/main.md:39-42`; `src/PDEs/euler.jl:84-91,99-110` contain `NCRepresentation` methods that cannot be reached.
- **Scenario:** `build_equation(Dict(:name => :euler, :D => 1, :gamma => 1.4, :representation => :primitive), Dict(:T => Float64))` → `UndefVarError: Primitive not defined in HyperCloud` (same for `:lagrangian`); inside a runner this becomes a logged error and `nothing`.
- **Evidence:** `probe_runs.out`, testset "documented :primitive / :lagrangian representations build" (2 failures).
- **Fix:** either remove the non-conservative parsing and docs (and the unreachable `NCRepresentation` methods), or implement the types (and the NC flux/jump API the Euler equation would then need) and test them. At least make `_parse_representation` raise a clear "not supported" error.

#### 6. `solve_equation` stops silently before `tmax`; the runner reports success — medium — CONFIRMED
- **Where:** `src/time_integration.jl:122-125` (`if dt_val <= T(1e-12); break; end`), `:174-176` (final save), runners `src/SimulationFunctions/direct.jl:73-95` (no check of the final time).
- **What/scenario:** when the CFL time step collapses (a blowing-up or near-vacuum state gives a huge `max_eigenvalue`) the loop breaks, the last snapshot is stored with the actual (earlier) time, intermediate snapshots stay unassigned and are dropped, and `run_direct_simulation` returns a normal `SimData`. Statistics against a reference then look plausible. A NaN `dt` (NaN states) also passes the `<= 1e-12` test and ends the loop with `t = NaN`.
- **Evidence:** `probe_blowup.out`: Sod, MUSCL2 without limiter, CFL 4, tmax 0.2 → `sim.t = [0.0, 0.1104, 0.1104, 0.1104]`, 1 step, 4 instead of 5 snapshots, no warning or error, `sim !== nothing`.
- **Fix:** after the loop, if `!(t ≈ tmax)` (or `!isfinite(dt_val)` inside the loop) throw an error (the runner then logs it and returns `nothing`) or at least `@warn` and record a stat; also check `isfinite(dt_val)` before stepping.

#### 7. `:snapshots => 0` makes every run fail — low — CONFIRMED
- **Where:** `src/time_integration.jl:104` (`range(zero(T), tmax_val, length = snapshots + 1)`).
- **Scenario:** `snapshots = 0` → `ArgumentError: range(0.0, stop=0.1, length=1): endpoints differ`, caught by the runner → `nothing`. (Had it not thrown, the final state would not be saved either: the post-loop save at `:174` requires `snap_counter ≤ snapshots + 1`.)
- **Evidence:** `probe_examples.out`, testset "snapshots = 0 keeps the final state".
- **Fix:** validate `snapshots ≥ 1` with a clear message, or define `snapshots = 0` as "final state only".

#### 8. BGK collision with `τ = 0` returns NaN — low — CONFIRMED
- **Where:** `src/SourceTerms/bgk.jl:42-43` (`λ = dt/τ`; `(f + λ f_eq)/(1 + λ)` with `λ = Inf` → `Inf/Inf`), `:35` (explicit: division by zero); `src/Builder/equations.jl:74-75` accepts any `:tau`.
- **Scenario:** `ConstantRelaxationTime(0.0)` (a natural way to ask for the "Euler limit") → `implicit_solve` gives an all-NaN state; the docstring says "`τ → 0` projects onto the equilibrium".
- **Evidence:** `probe_analytic.out`, testset "BGK collision with tau = 0".
- **Fix:** return `f_eq` when `isinf(λ)` (and reject `τ ≤ 0` for the explicit form), or validate `tau > 0` in `build_equation(:bgk)`.

#### 9. Burgers Gauss closure: Float32 Newton tolerance unreachable → warning flood — low — CONFIRMED
- **Where:** `src/PDEs/burgers.jl:42` (`tol = T(1e-10)`, absolute), `:69`, `:75` (`@warn` per evaluation).
- **Scenario:** `analytical_solution(merge(params, :real_type => Float32))` for a Gaussian: 11 of 41 pre-shock evaluations at t = 0.5 emit "Newton-Raphson did not converge" (the iterate oscillates by one ulp); the values are fine (max deviation from Float64 9.2e-8). Evaluated on a reference grid this means thousands of warnings and 100 Newton iterations per point.
- **Evidence:** `probe_analytic.out` ("nwarn = 11"), `probe_misc_t1.out` ("d = 9.18e-8").
- **Fix:** relative tolerance like `4eps(T) * max(1, |u|)`, or stop when the step stops decreasing; warn once per closure, not per point. (The same absolute-tolerance pattern is in the Euler Newton, `src/PDEs/euler.jl:147`, which is harmless there: 100 iterations, result within 1e-6 of Float64.)

#### 10. Exact Euler Riemann solver throws on vacuum-generating data — low — CONFIRMED
- **Where:** `src/PDEs/euler.jl:143-153` (no pressure-positivity/vacuum check), crash at `:194` (`(c_final / c_R)^(2/(γ-1))` with `c_final < 0`; same pattern at `:177`).
- **Scenario:** `uL = (1, -6, …)`, `uR = (1, +6, …)` with `p = 1` (`Δu = 12 > 2(c_L + c_R)/(γ-1) = 11.8`): `p*` is clamped to `1e-9`, the fan formulas are evaluated beyond the vacuum front and `exact(SVector(x, 0.2))` throws `DomainError … Exponentiation yielding a complex result`.
- **Evidence:** `probe_misc_t1.out`, testset "Euler exact solution with vacuum generation conserves mass".
- **Fix:** test the pressure-positivity condition and return the vacuum solution (ρ = p = 0 between the two rarefaction tails `u_L + 2c_L/(γ-1)` and `u_R - 2c_R/(γ-1)`), or error with a clear message.

#### 11. Other suspicions (not settled)
- **SUSPECTED, low:** `src/PDEs/linear_advection.jl:68` checks commutation with `isapprox(...; atol = 1e-12)` only (rtol becomes 0 when atol is given), so commuting matrices with large entries or Float32 entries could be rejected spuriously. My probe (A₂ = A₁²/37, entries O(10)) happened to give an exactly zero commutator, so it did not trigger. A relative tolerance `rtol = sqrt(eps(T))` is safer.
- **SUSPECTED, low:** the Burgers closures (`burgers.jl:90-168`) ignore periodic wrap; on a periodic domain a Riemann or Box IC has a second interface at the boundary and the Gauss characteristics wrap. Not used that way by the shipped examples/tests.

### Verdict

The physics core is in good shape: I re-derived the Euler fluxes/eigenvalues/conversions, Toro's exact
Riemann solver, the Burgers closures, the linear ray tracing, the relaxation Maxwellian and the BGK
entropic equilibrium (Chu reduction, dual Hessian, Gauss–Hermite weights) and found no errors; the probes
confirm Float32 parity (Sod, BGK), conservation, the claimed convergence orders and thread-count
independence. The default suite passes (924 tests, 68 s), but the `ka_cpu` variant fails (2-D BGK, Finding 1). The defects are at the edges and in the workflow:
one shipped example (`burgers_kinetic`) is broken twice over — a nonexistent kinetic method and a
reference used past shock formation — and the `examples` test group cannot detect this (no assertions,
cached results); a documented representation option crashes; and the time loop can end early while the
runner reports success. None of these affect the equation kernels, but Findings 1–6 should be fixed
before the examples or the runner statistics are relied on.
